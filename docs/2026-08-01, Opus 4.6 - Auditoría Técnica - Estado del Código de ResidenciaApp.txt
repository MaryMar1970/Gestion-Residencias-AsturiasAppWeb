🔴 Problemas Críticos (deben resolverse)
1. Archivos frontend GIGANTES — Imposible de mantener
Reservas.tsx
 tiene 164 KB (~4.000+ líneas) en UN SOLO archivo. Contiene al menos 6 componentes mezclados:

CalendarioGantt
ReservaDetalleModal
NuevaReservaModal
ReservasPage
BloqueosPage + BloqueoModal
HuespedesPage (Solicitudes)
App.tsx
 tiene 64 KB.

Impacto: Cualquier cambio pequeño en el calendario puede romper la lógica de bloqueos o solicitudes. Es imposible que dos personas trabajen en paralelo. El rendimiento del editor/IDE se degrada.

Solución: Extraer cada componente a su propio archivo + crear hooks personalizados (useReservas, useCalendario, useHuespedes).

2. Lógica de evaluación DUPLICADA entre frontend y backend
La matriz de prioridades (~30 reglas) está copiada literalmente en DOS sitios:

Backend — 
ReservasService.cs
 en EvaluarReserva():

csharp

var matriz = new Dictionary<string, string>
{
    { "comisión no indem.|gc|viogen", "1, 1, 1" },
    { "comisión no indem.|gc|activo", "1, 1, 2" },
    // ... 30+ entradas hardcodeadas
};
Frontend — Reservas.tsx en calcularEvaluacion(): idéntica copia.

Impacto: Si añades una regla en el backend pero olvidas el frontend (o viceversa), los resultados serán inconsistentes. Además, esta matriz debería ser configurable desde la base de datos, no hardcodeada.

Solución:

Mover la matriz a una tabla de BD (ReglaEvaluacion) o a SystemSettings como JSON
Crear endpoint GET /api/configuracion/matriz-evaluacion
El frontend la descarga y la usa — fuente única de verdad
3. Race condition en numeración de facturas
En 
FacturaService.cs
, el método SiguienteNumeroAsync:

csharp

var ultimoOrden = await db.Facturas
    .Where(f => f.Serie == serie && f.Ejercicio == ejercicio)
    .MaxAsync(f => (int?)f.NumeroOrden) ?? 0;
var orden = ultimoOrden + 1;  // ← NO es atómico
Impacto: Si dos usuarios generan facturas simultáneamente, pueden obtener el mismo número de factura. El índice único lo atrapará como excepción no controlada, pero la operación fallará sin reintentar.

Solución: Usar una tabla de contadores con UPDLOCK o ExecuteSqlRaw con UPDATE ... SET numero = numero + 1 OUTPUT INSERTED.numero, o envolver en transacción con retry.

4. HabitacionId = Guid.Empty como sustituto de null — Code smell
En 
Reserva.cs
:

csharp

public Guid HabitacionId { get; set; }  // Non-nullable Guid
Pero en el código se asigna Guid.Empty cuando la solicitud es denegada:

csharp

if (esNegativeResolucion)
{
    assignedHabitacionId = Guid.Empty;  // ← Simula null con Guid.Empty
}
Impacto: Guid.Empty no es un FK válido — no hay ninguna Habitación con Id = 00000000-0000-0000-0000-000000000000. Esto rompe la integridad referencial. El DbContext lo permite porque la relación está configurada como IsRequired(false), pero el tipo C# no es nullable.

Solución: Cambiar a public Guid? HabitacionId { get; set; } y usar null en lugar de Guid.Empty.

5. N+1 Queries en búsqueda de disponibilidad
En ReservaService.GetHabitacionesDisponiblesAsync():

csharp

foreach (var h in todasHab)
{
    var solapamiento = await ComprobarSolapamientoAsync(h.Id, ...);
    // ↑ UNA query SQL por cada habitación
    if (!solapamiento.HaySolapamiento)
        libres.Add(...);
}
Impacto: Si hay 50 habitaciones, se ejecutan 50 queries SQL para una sola búsqueda de disponibilidad. Con carga concurrente, esto se convierte en un cuello de botella.

Solución: Una sola query que excluya habitaciones ocupadas:

csharp

var habOcupadas = await db.Reservas
    .Where(r => r.Habitacion.ResidenciaId == residenciaId
        && r.Estado != EstadoReserva.Cancelada
        && r.FechaEntrada < salida && r.FechaSalida > entrada)
    .Select(r => r.HabitacionId)
    .Distinct().ToListAsync();
var libres = await db.Habitaciones
    .Where(h => h.ResidenciaId == residenciaId && h.Activa
        && !habOcupadas.Contains(h.Id))
    .ToListAsync();
6. Ausencia total de tests
No hay ningún proyecto de test (*.Tests.csproj) en toda la solución. Ni unitarios, ni de integración, ni E2E.

Impacto: Cada cambio es un riesgo. La lógica de evaluación con 30+ reglas, la resolución automática, la facturación — todo se verifica manualmente.

Solución: Crear ResidenciaApp.Tests con al menos:

Tests de EvaluarReserva() para cada combinación de la matriz
Tests de CalcularResolucionAutomatica() para los casos límite
Tests de ComprobarSolapamientoAsync() incluyendo turnover
Tests de SiguienteNumeroAsync() verificando secuencialidad
🟡 Problemas Importantes (deberían resolverse)
7. Resolución usa "magic strings" en vez de enum
EstadoReserva es un enum (✅), pero Resolucion es un string con valores mágicos dispersos por el código:

csharp

// Aparecen en 15+ sitios distintos:
r.Resolucion == "SI"
r.Resolucion == "NO"
r.Resolucion == "CONCEDIDA"
r.Resolucion == "DENEGADA"
r.Resolucion == "DESESTIMADA"
r.Resolucion == "RENUNCIA"
r.Resolucion == "REEVALUADA"
Impacto: Un typo como "DENAGADA" pasaría desapercibido y causaría bugs silenciosos.

Solución: Crear enum Resolucion o al menos una clase estática con constantes.

8. Raw SQL de migración en Program.cs
csharp

dbContext.Database.ExecuteSqlRaw(@"
    IF NOT EXISTS (SELECT * FROM INFORMATION_SCHEMA.COLUMNS 
    WHERE TABLE_NAME = 'Habitaciones' AND COLUMN_NAME = 'TipoCamaPrincipal')
    BEGIN
        ALTER TABLE [Habitaciones] ADD [TipoCamaPrincipal] nvarchar(10) NOT NULL DEFAULT 'IND';
    END
    ...
Impacto: Esto bypassea las migraciones de EF Core. Si alguien ejecuta dotnet ef migrations pensando que el schema está sincronizado, habrá discrepancias. Además, el SQL es específico de SQL Server — rompe la compatibilidad con SQLite.

Solución: Crear migraciones EF Core formales para estos cambios y eliminar el SQL raw.

9. "Healing routines" al inicio — Indica invariantes rotos
csharp

// Healing routine for cancelled reservations
var cancelledReservations = dbContext.Reservas
    .Where(r => r.Estado == EstadoReserva.Cancelada && r.NumeroOrden > 0)
    .ToList();
// ... resetear NumeroOrden a 0
// Healing routine for reservation order numbers
var reservationsToHeal = dbContext.Reservas
    .Where(r => r.NumeroOrden == 0 && r.HuespedId != null && !r.EsBloqueo ...)
    .ToList();
// ... reasignar NumeroOrden
// Healing routine for empty Resolucion
var reservationsWithoutResolution = dbContext.Reservas
    .Where(r => r.Resolucion == null || r.Resolucion == "")
    .ToList();
Impacto: Estas 3 rutinas de "sanado" se ejecutan cada vez que arranca la aplicación y existen porque en algún momento se crearon reservas con datos inconsistentes. Esto indica que los servicios de creación/actualización no están garantizando los invariantes.

Solución: Corregir la raíz del problema en CreateAsync/UpdateAsync para que nunca generen datos inconsistentes, y eliminar las healing routines.

10. ReservasService.cs — Demasiadas responsabilidades en un archivo
ReservasService.cs
 tiene ~40KB y contiene:

IHuespedService + HuespedService (CRUD huéspedes)
IReservaService + ReservaService (CRUD reservas, validación, evaluación, calendario, disponibilidad, reevaluación)
NaturalStringComparer
Son al menos 3 servicios en un solo archivo. El método CreateAsync solo tiene ~100 líneas mezclando validación, cálculos, persistencia y lógica de negocio.

Solución: Separar en HuespedService.cs, ReservaService.cs, EvaluacionService.cs, DisponibilidadService.cs.

11. Sin transacciones explícitas en operaciones críticas
La creación de reserva hace:

Busca/crea huésped → SaveChangesAsync()
Crea reserva → SaveChangesAsync()
Si el paso 2 falla, el huésped ya se creó. No hay IDbContextTransaction:

csharp

// En CreateAsync:
var huesped = await CrearOActualizarHuespedAsync(dto.Huesped);  // SaveChanges interno
// ... lógica ...
db.Reservas.Add(entity);
await db.SaveChangesAsync();  // Segundo SaveChanges
Solución: Envolver operaciones multi-paso en using var tx = await db.Database.BeginTransactionAsync().

12. Sin paginación real en endpoints de listado
csharp

// ReservasService.GetAllAsync - devuelve TODAS las reservas de una residencia
return await q.OrderBy(r => r.FechaEntrada)
    .Select(r => ToDto(r)).ToListAsync();  // Sin Take/Skip
// BuscarReservasAsync - hardcoded a 100
.Take(100).ToListAsync();
Impacto: Con miles de reservas históricas, las respuestas serán enormes y lentas.

Solución: Añadir parámetros page/pageSize y devolver PaginatedResult<T> con total count.
